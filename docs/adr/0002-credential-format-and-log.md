# ADR-0002: Credential format, signing, and transparency log

- Status: Accepted
- Date: 2026-10-20

## Context

The MVP must issue credentials, verify them online and offline, revoke them
without publishing personal data, and append every issuance and revocation to a
tamper-evident log. The format, canonicalization, and proof layout need to be
stable before more code depends on them.

## Decision

- A credential is `SignedCredential { claims: CredentialClaims, signature_hex }`.
  `CredentialClaims` carries `credential_id`, `issuer`, `subject`,
  `credential_type`, an object of application claims, and an optional `key_id`.
  `key_id` is omitted when absent so credentials issued before key ids remain
  byte-identical and verifiable.
- `credential_id` is a UUID generated by `verifier-core` and is signed inside
  the claims, so the id cannot be swapped after issuance.
- Sign the canonical JSON of `CredentialClaims` with Ed25519. Canonicalization
  is `serde_json::to_vec` over the typed struct, which is deterministic for the
  fixed field set and nested `serde_json::Value` maps. The verifier signs and
  verifies the exact same bytes.
- Store signing seeds as hex in `issuer_keys.signing_seed_hex` for the MVP.
  This is development key storage, not production. `issuers.signing_seed_hex`
  is retained as a legacy fallback for credentials issued before key ids
  existed; new issuers mirror their initial key seed there for compatibility.
- Append to the transparency log with a SHA-256 Merkle tree. Leaf hash is
  `SHA256(0x00 || payload)` and node hash is `SHA256(0x01 || left || right)`.
  The tree follows RFC 6962: split at the largest power of two smaller than the
  tree size, and promote an unpaired node rather than duplicating it. This makes
  roots prefix-consistent. An inclusion proof is the sibling path from the leaf
  to the current root.
- Revocation is a signed-off credential status plus a `revocation_entries` row
  and a `revoked` transparency-log event. Verifiers get the current status from
  the API or from a downloaded status list. No personal data is written to the
  log; revocation events reference the credential id only.

## Consequences

- Online and offline verifiers can share `verifier-core` and agree on the exact
  signed bytes.
- The CLI can verify a signed credential and a Merkle proof without contacting
  the API, and it detects revocation from a downloaded status list.
- Changing the claim field set or canonicalization is a breaking change and
  needs a versioned credential format. Adding optional `key_id` with
  `skip_serializing_if` preserves legacy signed bytes.
- Key ids, rotation, key revocation, and consistency proofs are implemented in
  ADR-0003. KMS/HSM, automated monitors, and gossip remain deferred.
- The RFC 6962 tree shape is a breaking change for roots and inclusion proofs
  created by the earlier duplicate-last-node implementation. The MVP database
  is reset for this slice.

## Alternatives considered

- Sign the raw HTTP response body or a database row: rejected because
  serialization details would change between API and verifier.
- Start with the W3C Verifiable Credentials data model and a JWS proof:
  rejected for this slice because it needs its own format decision, test
  vectors, and selective-disclosure design.
- Store revocation status inside the log only: rejected because offline
  verifiers need a compact downloadable status list.
